Reorder anything. Save one row.

Staquia gives every item of a list a short position string. Sort by it and you get the order back. Move an item and only that item changes, its neighbors are never touched.

Try it: drag the items, add new ones, and compare the rows each approach would write.

The text at the bottom of each item is its position. Sort the positions as plain strings and you get exactly the order you see. With an integer index column (0, 1, 2…) every item between the old and the new place must be rewritten, Staquia only rewrites the moved one.

The library has zero dependencies and is shipped as an ES module. In the browser you can also import it directly from a CDN:

html 
<script type="module">
  import Staquia, { LexicalList } from "https://cdn.jsdelivr.net/npm/staquia@0.5.1/+esm";
</script>

The crate has zero dependencies and no unsafe code. It creates the same positions as the JavaScript library, so a Rust server and a JavaScript app can share the same rows.

Quick start

Give each item a position and let a LexicalList keep them in sync (your type implements the Item trait):

javascript 
import Staquia, { LexicalList } from "staquia";

// Plain ASCII positions, ready for production (other presets in the Setup chapter)
const system = Staquia.ascii();
const list = new LexicalList(system);

// Any object with an "id" and a "position" field
const milk = { id: 1, text: "Milk", position: "" };
const meat = { id: 2, text: "Meat", position: "" };
const bread = { id: 3, text: "Bread", position: "" };
list.push(milk);
list.push(meat);
list.push(bread);

// Move the bread between the milk and the meat
const moved = list.move(3, 1, 2);
if (moved.ok) {
  // Only bread.position changed, save only that item
}
rust 
use staquia::{Item, LexicalList, Position, Staquia};

// Any type with an id and a position field
struct Product {
    id: u32,
    text: String,
    position: String,
}

impl Item for Product {
    type Id = u32;
    fn id(&self) -> &u32 { &self.id }
    fn position(&self) -> &str { &self.position }
    fn set_position(&mut self, position: &Position) { self.position = position.to_string(); }
}

fn main() -> Result<(), staquia::Error<u32>> {
    // Plain ASCII positions, ready for production (other presets in the Setup chapter)
    let system = Staquia::ascii();
    let mut list = LexicalList::new(system);

    list.push(Product { id: 1, text: "Milk".into(), position: String::new() })?;
    list.push(Product { id: 2, text: "Meat".into(), position: String::new() })?;
    list.push(Product { id: 3, text: "Bread".into(), position: String::new() })?;

    // Move the bread between the milk and the meat
    let moved = list.move_to(&3, Some(&1), Some(&2))?;
    // Only the bread's position changed, save only that item
    println!("{}", moved.value().position);
    Ok(())
}

Introduction

This project was created to solve the reinsertion problem in lists.

Imagine a list where the items can change their order: tasks, a kanban board, a playlist, the rows of a table. It has A, B and C with the positions 1, 2 and 3. When A moves between B and C, the positions of every item in between must be rewritten to store the new order. And that is not the only thing to worry about:

  • Performance issues with very long lists: a random move rewrites about a third of the list.
  • Which items must be updated after a move, and which ones can stay as they are?
  • Each move becomes many writes in the database, one per shifted item.
  • When recovering a deleted item, its old position may be taken now, so it needs a new one and the list must be sorted again.
  • If the user works offline, or many users edit the same list, every change must be synchronized, and the more items each move touches, the more conflicts appear.

This is what Staquia was created for!

Each item stores a short position string. When an item moves, only its own position changes: one move, one write. You already saw it in the list of Get Started.

There are other ways to get "a value between two values", so the next chapter, Why Staquia, compares them. After that, the chapters explain how Staquia works, starting with how a string can keep an order: Strings.

Why Staquia?

Every list that users can reorder has to store its order somewhere. There are several common ways to do it, and they all look fine with five items on a developer's machine. The differences appear with long lists, a real database, offline users and items moved many times into the same place.

The usual approaches

Approach Rows written per move Moves into the same gap When it runs out Sorted by the database
Integer index
0, 1, 2…		 Every item between the old and the new place, about a third of the list on average (35 rows in a list of 100) Unlimited Never, it just keeps rewriting Yes
Gaps
1000, 2000…		 1, until a gap is full 9 with gaps of 1000 The whole list must be renumbered Yes
Floats
1.5, 1.25…		 1 52 Silently: the middle value equals a neighbor and two items share a position Yes

The numbers are not estimates: they were measured. Splitting the same gap of two floats works 52 times, a gap of 1000 works 9 times, and moving a random item in a list of 100 with an integer index rewrites 35 rows on average.

What makes Staquia different

1. One write per change

Moving, inserting or restoring an item writes one row. And you don't have to guess which one: the LexicalList returns the affected items of every operation, the only ones that need to be saved.

2. Stacking is free

Most changes are not moves but items added at the start or the end. The segment N handles them like a counter, so stacked positions never get longer. The alphabet system stacks 7 174 453 items in each direction before N runs out, the default system about 5.7 × 1014. See Segments.

3. Predictable limits, with a warning

Positions only grow when items are moved again and again into the same gap, and you can calculate how many moves fit before it happens. A threshold warns you before the limit, so you can space the positions again while there is still room. Nothing is ever lost silently. See Maths, where you can also watch it happen.

4. Errors are values

Nothing is thrown. Every operation returns a Result that you check in the same place, and a failed list operation leaves the list and your objects exactly as they were. See Error Handling.

javascript 
const moved = list.move(id, previousId, nextId);
if (moved.ok) save(item); // One row
else if (moved.error.type === "position") rebalance(); // Rare, and you decide when
rust 
match list.move_to(&id, previous, next) {
    Ok(moved) => save(moved.value()), // One row
    Err(LexicalError::Position(_)) => rebalance(list)?, // Rare, and you decide when
    Err(error) => return Err(error.into()),
}

5. Your own alphabet

You choose the digits. Plain ASCII letters for positions that travel in URLs, or a large range of unicode characters for shorter positions. Different systems can live in the same application, and positions can be migrated from one configuration to another keeping their order. Try it in the Setup App.

6. Made for databases

Positions are plain strings with a known maximum length. The database sorts them with a normal index, every move is a single UPDATE, and moves in different places never touch the same rows. See the Database chapter.

7. Light

Zero dependencies, a single ES module, and positions are plain data objects: they keep no reference to the system or the list, so nothing stays alive longer than you need it.Zero dependencies and no unsafe code. Positions are small Copy values on the stack: they keep no reference to the system or the list, and creating one never allocates.

When Staquia is not the right tool

  • The list is never reordered by hand: an auto increment id or a timestamp is enough.
  • The order comes from the data (a date, a name, a price): sort by that field instead.
  • The whole list is always saved at once (a small array inside one document or a local file): just store the array in order.
Note:  Staquia keeps the order, not the meaning of the items. Two users moving two items into the same gap at the same time can get the same position, the Database chapter shows how to detect it and how the list repairs it.

Appending never makes positions longer: N works like an integer, so the next position just adds one to it. The numbers of each system are in the Setup App and the formulas in the Maths chapter.

When not to use Staquia

  • Peer to peer editing without a server, offline first: two people moving items into the same gap at the same time get the same position, and the conflict is solved when the rows reach the database (see the Database chapter). Without a central database, a CRDT avoids that coordination.
  • Lists sorted by a field like a date or a name: sort by that field, there is no manual order to keep.
  • Small lists saved whole, like a short array in a JSON column: saving the array is simpler.
Note:  Coming from another approach? Load your rows sorted by their old key and pass them to list.set(rows, { untrusted: true })list.set_untrusted(rows) with an empty position: every row gets a Staquia position in the same order, and you save them once. The Database chapter shows the migration.

Strings and Comparison

This algorithm relies on how programming languages compare strings. Each character has a number in the Unicode standard, and two characters are compared by those numbers. They are usually written in hexadecimal, like the RGB colors.

javascript 
// "a" is the unicode character "a", its number is 0x61
let a = "a";
// "z" is the unicode character "z", its number is 0x7A
let z = "z";
// Prints true, as 0x61 < 0x7A
console.log(a < z);
rust 
// "a" is the unicode character "a", its number is 0x61
let a = "a";
// "z" is the unicode character "z", its number is 0x7A
let z = "z";
// Prints true, as 0x61 < 0x7A
println!("{}", a < z);

So a and z can be treated as numbers. They will become the digits of a Number System, and their place in it is decided by their unicode number. From now on that value will be called their weight.

When a string has many characters, they are compared one by one, left to right, and the first different character decides which string is bigger. The rest of the string doesn't matter.

Comparing a and ab, the first character is the same "a", so the next one is checked. a has no second character, and a missing character weighs less than any character, so ab is bigger. But b is bigger than ab, because its first character b already weighs more than a.

a
<
ab
<
b

The next chapter shows how all of this is used to create a Number System.

Note: When comparing strings, the length is not important, the position of each character is.
Note:  Databases compare strings too, but many of them ignore symbols or the letter case by default. Positions must be compared byte by byte (a binary collation) so the database order matches the library order. The Database chapter shows how.

Number System

To take advantage of string comparison, Staquia builds a lexicographic number system: a system where the digits are characters. Using characters instead of 0 to 9 gives a much bigger set of digits, so big numbers can be written with very few characters.

A Staquia number system follows these rules, or better said, axioms:

  • It has a zero digit called zero.
  • It has a first digit called first and a last digit called last.
  • Their unicode values must be zero < first < last.
  • The digits are the zero plus every character from first to last, so the set contains at least 3 digits.
  • The number of digits, including the zero, is the base of the system: b = (last - first) + 2
  • No negative numbers exist.
  • The middle digit is the one in the middle of the set, rounded upwards: middle = ceil((first + last - 1) / 2)

This is how the set looks like

  • a → 1
  • b → 2

  • f → 6

  • h → 8
  • i → 9
  • j → 10
  • k → 11
  • l → 12
  • m → 13
  • n → 14
  • o → 15
  • p → 16
  • q → 17
  • r → 18
  • s → 19
  • t → 20

With ! as the zero and the letters from a to z, this is a base 27 system and its middle digit is m. A word is just a number written with these digits:

  • ! (\u0021) as the zero
  • ° (\u00B0) as the first digit
  • ұ (\u04B1) as the last digit
That is a base 1027 system.

Positions

This chapter starts with something that may sound obvious: numbers exist to count and enumerate things. Before you say "Isn't that obvious!", it is mentioned to not forget how powerful they are for sorting.

Whenever you need a list, numbers are there to give each item its position.

So, with the Number System from the previous chapter, from now on our numbers will also be called positions. You may have done this before without noticing, like in a market list:

To buy in the market
  1. 🥛 Milk
  2. 🥩 Meat
  3. 🍞 Bread

In this list the letters work like numbers to sort the items. Adding an item at the end is easy, it takes the next letter. But what if an item must be prioritized over another one?
Then the positions must be reassigned and the items reordered.

Reinsertions

Moving an item that is already in a list to a new place will be called a reinsertion. As the Positions chapter showed, it is not as easy as it looks.

The goal is to avoid rewriting the positions of the other items. It is the same problem when a new item is inserted in a specific place, or when a deleted item is recovered with its original position.

Start with numbers: what value fits between 1 and 2?
The average 1.5. The new item takes that position and it is already between its neighbors, nothing else changes.
This is the basic principle of the reinsertion algorithm and how it avoids rewriting the list.

The reinsertion cycle can start again safely 🔄.
Notice that the position got one digit longer to make room. This is very important in the Maths chapter.

Most of the time, though, items are not reinserted but stacked: added at the start or the end of the list. Those don't need to take the middle of a gap at all.

That's why a Staquia position is divided into Segments: one to stack items without making them longer, and one for the reinsertions.

Note:  These examples use single letters to keep them short, so they run out of room after only 5 reinsertions. Real positions have many more digits, the Maths chapter shows exactly how many reinsertions fit.
Note:  This is only the basic idea, so don't worry if the positions Staquia generates look different. Two improvements are applied:
  • Trailing zeroes are dropped when they are not needed, so the positions stay short and the string comparison stays fast.
  • A position is divided into Segments, so the reinsertion algorithm is only used when it is really needed.

Segments

The Reinsertions algorithm makes positions longer each time it is used. But most of the time items are just stacked at the start or the end of a list, and that shouldn't make positions longer.

So a Staquia position is divided into two segments, one for each job. It looks like nnnnnz…: the first ln characters are the segment N and the rest is the segment Z.

javascript 
import Staquia from "staquia";

// The alphabet: zero "!", digits "a" to "z", ln = 5, lz = 15
const system = Staquia.create("!", "a", "z", 5, 15, 0.15);

// The first position: N is the middle digit repeated, Z is a zero
const start = system.start(); // "mmmmm!" → N = "mmmmm", Z = "!"
rust 
use staquia::Staquia;

// The alphabet: zero '!', digits 'a' to 'z', ln = 5, lz = 15
let system = Staquia::create('!', 'a', 'z', 5, 15, 0.15)?;

// The first position: N is the middle digit repeated, Z is a zero
let start = system.start()?; // "mmmmm!" → N = "mmmmm", Z = "!"

Segment N

The segment N has a fixed length (ln, 5 by default) and works like a short integer. Stacking an item after another one is just adding 1, and stacking it before is subtracting 1, so the position never gets longer.

For instance, 1 in this system is a. Moving forward one position from d looks like this:

With unicode values it would look like this:

javascript 
// The unicode number of "d"

// Subtract 1 and turn it back into a string

// Subtract 1 and turn it back into a character
let c = (d - 1) as char;
println!("{c}"); // "c", the previous character before "d"

Staquia does the same over the whole segment, carrying to the next digit when needed:

javascript 
system.next(start); // "mmmmn!"
system.previous(start); // "mmmml!"

// The start is the middle of N, so there is room to stack on both sides
system.next(system.forge("!!!!a")); // "!!!!b!"
rust 
system.next(&start)?; // "mmmmn!"
system.previous(&start)?; // "mmmml!"

// The start is the middle of N, so there is room to stack on both sides
system.next(&system.forge("!!!!a")?)?; // "!!!!b!"

Since N has a fixed length, it has a last value (zzzzz) and a first one (!!!!!). Stacking past them fails with an OverflowErrorPositionError::EdgeReached, see Error Handling.

When a shorter string is turned into a position with forge, N is completed with zeroes to the right: d becomes d!!!!. As the Reinsertions chapter showed, zeroes on the right keep the order of the strings.

Segment Z

This is the segment where the reinsertion algorithm is used.

Its length is flexible, up to lz digits (15 by default). It grows when there is no room left between two positions, and shrinks when its trailing zeroes can be dropped.

The average weight of two numbers is their sum divided by 2, rounding upwards:

With unicode values:

javascript 
let a = "a".charCodeAt(0);

let a = b'a';
let z = b'z';

// Sum both values, divide them by 2 and round upwards

In Staquia the function that finds a position between two others is core. When N still has room between them it is used first, and only adjacent positions need Z:

javascript 
// There is room in N between "a!!!!!" and "b!!!!!"
system.core(system.forge("a"), system.forge("b")); // "ammmn!"

// "mmmmm!" and "mmmmn!" are adjacent, Z takes the middle
system.core(start, system.next(start)); // "mmmmmn"
rust 
// There is room in N between "a!!!!!" and "b!!!!!"
system.core(&system.forge("a")?, &system.forge("b")?)?; // "ammmn!"

// "mmmmm!" and "mmmmn!" are adjacent, Z takes the middle
system.core(&start, &system.next(&start)?)?; // "mmmmmn"

N stacks items fast and without growing, Z makes room for the reinsertions. But how do you choose the best Number System for your needs? The next chapter, Maths, shows how to measure it.

Maths

The Segments chapter ended with a question: how do you choose the best Number System for your needs? The answer is maths!
As said all along the documentation, positions are just numbers, so it is possible to calculate exactly how much they can take.

Halves and Cakes

First, how many times can a gap be split in half before it runs out of room?

Suppose you have a cake 🎂 cut in 16 equal slices, let's call this number b. You organize a race, and each competitor that reaches the goal gets half of the slices you have left. But the last slice is always yours.

Competitors
  • 1st place gets 8 slices
  • 2nd place gets 4 slices
  • 3rd place gets 2 slices
  • 4th place gets 1 slice
  • The last slice is yours 😋

The cake lasted 4 places, since a slice can't be cut again. That limit will be called hmax, and it is calculated as hmax = ceil(log2(b)).

Each digit of Z is a cake with b slices (the base of the system), and the slice you keep is the neighbor that already has that position. When b is not a power of 2 the halves can't be exact, so depending on the direction of the moves a digit lasts between floor(log2(b)) and ceil(log2(b)) halvings.

Calculating the length

The length l of a position is the fixed length of the segment N (ln) plus the current length of the segment Z (Δl):
l = ln + Δl

The maximum length lmax is the length of N plus the maximum length of Z (lz):
lmax = ln + lz

Overflow

There is an overflow when there is no valid position to return: a generated position is longer than the maximum (l > lmax), or N is already at its last value for next (or its first one for previous). Staquia returns an OverflowErrora PositionError::Overflow (or EdgeReached for N) so you can handle it.

Threshold

Waiting for the overflow would be too late, so a threshold gives an early warning. It is set with the factor kappa (fϰ), a value from 0 to 1:
lϰ = ceil((1 - fϰ) lmax)

When a position's length reaches lϰ, the result fails with a ThresholdReachedErrorPositionError::ThresholdReached. The position is still valid and comes inside the error, but it is time to space the positions again (see Error Handling).

By default the factor kappa is 0.15.

How many moves fit in the same gap?

This is the number that really matters. Stacking with N never makes positions longer, and moving items to different places doesn't add up either: Z only grows when items are moved again and again into the same gap.

Positions start with one digit in Z, and the threshold is reached at lϰ, so lϰ - ln - 1 digits of Z can be split before the warning. With the halvings of each digit, the moves into the same gap are between:
floor(log2(b)) (lϰ - ln - 1) and ceil(log2(b)) (lϰ - ln - 1)

Playground

The list below uses a tiny system on purpose: the alphabet with ln = 2 and lz = 3, so lmax = 5, lϰ = ceil(0.85 × 5) = 5, and only 4 (5 - 2 - 1) = 8 to 5 (5 - 2 - 1) = 10 moves fit into the same gap.

Keep dropping items right after the first one. Each drop takes the middle of the same shrinking gap, so the position gets longer. When the threshold is reached, the list spaces every position again (the rows written jump for that move) and the cycle starts over. Stacking with the + button never makes positions longer.

Example: the alphabet as a number system

The system used all along has the base b = 27, with the default lengths ln = 5 and lz = 15. So:

  • hmax = ceil(log2(27)) = 5 halvings per digit at most.
  • lmax = ln + lz = 5 + 15 = 20, an overflow happens with positions longer than 20 characters.
  • lϰ = ceil((1 - 0.15) 20) = 17, the threshold is reached by positions with 17 characters.
  • 4 (17 - 5 - 1) = 44 to 5 (17 - 5 - 1) = 55 moves fit into the same gap before the threshold.

The default system has the base 1027, so the same gap takes 110 to 121 moves. You can try other values in the Setup App.

Note:  Bigger is not always better! hmax grows with a logarithm: fast at the start and very slowly later. A system with the base b = 129 and another one with b = 256 both have an hmax of 8. Doubling the base adds only one halving per digit, while a longer Z adds hmax halvings per digit.
Note:  In maths and physics the "Δ" symbol is called delta, and it is used for values that change.

Error Handling

The Maths chapter showed that a position can reach the threshold or cause an overflow. Other things can fail too, like reading a position with characters that are not digits of the system.

Staquia never throws. Every function that can fail returns a Result, so you decide what to do, in the same place where it happened, without stopping the application:

typescript 
// A Result is either a success with its value, or a failure with its error
type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };
rust 
// The Result of the standard library: a success with its value, or a failure with its error
enum Result<T, E> {
    Ok(T),
    Err(E),
}
javascript 
const result = system.next(system.forge("zzzzz"));
if (result.ok) {
  result.value; // The position
} else {
  result.error; // Why it failed
}
rust 
match system.next(&system.forge("zzzzz")?) {
    Ok(position) => println!("{position}"), // The position
    Err(error) => println!("{error}"), // Why it failed
}

Example

You now know how the algorithm works. This chapter shows how to use it in an application, building the market list of the Introduction chapter.

You could call next, previous and core yourself, but Staquia includes a LexicalList: a list that keeps the order of your objects and their positions in sync, and tells you exactly which items must be saved.

When a drag and drop ends, your drag and drop library tells you where the item was dropped. Pass the ids of its new neighbors to movemove_to: undefinedNone as the previous one moves it to the start, and as the next one to the end. Only the moved item gets a new position.

fn on_drop(

Spacing the positions again

After many moves into the same gap the threshold is reached, and the move fails with a "position"LexicalError::Position error. rebalance spaces every position again keeping the current order, and returns the affected items:

javascript 
function onDrop(id, previousId, nextId) {
  let moved = list.move(id, previousId, nextId);
  if (!moved.ok && moved.error.type === "position") {
    // Keep the current order and space the positions again
    const rebalanced = list.rebalance();
    if (rebalanced.ok) {
      const [affected] = rebalanced.value;
      saveAll(affected.map((item) => items.get(item.id)));
    }
    moved = list.move(id, previousId, nextId);
  }
  if (moved.ok) save(items.get(id));
}
rust 
use staquia::LexicalError;

fn on_drop(
    list: &mut LexicalList<MarketItem>,
    id: u32,
    previous: Option<&u32>,
    next: Option<&u32>,
) -> Result<(), staquia::Error<u32>> {
    match list.move_to(&id, previous, next) {
        Ok(moved) => save(moved.value()), // The only item that changed
        Err(LexicalError::Position(_)) => {
            // Keep the current order and space the positions again
            for item in list.rebalance()? {
                save(item.value());
            }
            save(list.move_to(&id, previous, next)?.value());
        }
        Err(error) => return Err(error.into()),
    }
    Ok(())
}

Rebalancing rewrites many positions, but it happens rarely: only when one gap received dozens of moves. Every other operation writes a single item.

Database

Staquia was made for lists that live in a database. A position is a plain string with a known maximum length, so the database can store it, index it and sort it on its own. These are the benefits, and how to set it up.

Why it fits a database

  • One UPDATE per move. No renumbering, no long transactions, no locks over the whole list.
  • Sorted by an index. ORDER BY position reads the rows straight from an index, no recursive queries or sorting in your application.
  • Moves don't collide. Two users moving items in different places of the list write different rows, so they never block or overwrite each other.
  • Easy to synchronize. A change is just "this row now has this position". Offline changes can be sent later in any order, and the last value of each row wins.
  • Bounded size. A position never has more than lmax = ln + lz characters (20 by default), so the column and its index have a predictable size.

The table

Store the position in a text column and index it together with the list it belongs to. The database must compare the positions byte by byte (a binary collation), otherwise its order won't match the library order: many collations ignore symbols like the ! zero, or the letter case.

sql 
-- PostgreSQL
CREATE TABLE tasks (
  id       serial PRIMARY KEY,
  list_id  integer NOT NULL,
  title    text NOT NULL,
  position varchar(20) COLLATE "POSIX" NOT NULL,
  -- Two rows of the same list can't share a position (checked at the end of each transaction)
  CONSTRAINT tasks_position UNIQUE (list_id, position) DEFERRABLE INITIALLY DEFERRED
);

The unique constraint also creates the index used by ORDER BY. It is DEFERRABLE because a rebalance updates many rows in one transaction, and a new position may be equal to an old one that is updated a moment later.

DatabaseBinary collation
PostgreSQLCOLLATE "POSIX" or COLLATE "C"
MySQLutf8mb4_bin
SQL ServerLatin1_General_100_BIN2_UTF8 (or any _BIN2 collation)
SQLiteBINARY (the default)
MongoDBThe default string comparison, without a collation option

UTF-8 bytes keep the order of the unicode values, and JavaScript compares the same values as long as the digits are in theRust compares strings by those same bytes, and the systems only use digits of the Basic Multilingual Plane (up to U+FFFF), where JavaScript agrees too. That's why the library and the database always agree. Each of those characters takes at most 3 bytes, so a default position takes at most 60 bytes.

With an ORM

Declare the position as a plain string of at most 20 characters, and write the binary collation and the DEFERRABLE unique constraint of the table above in a SQL migration: most ORMs can't describe them in their schema.

  • Prisma: position String @db.VarChar(20), then create the migration with prisma migrate dev --create-only and add the collation and the constraint to its SQL before applying it.
  • Drizzle: position: varchar("position", { length: 20 }).notNull(), and the collation and the constraint in a custom migration made with drizzle-kit generate --custom.
  • SQLx (Rust): its migrations are plain SQL, so the table above is the migration (sqlx migrate add tasks), and the position is a String in your queries.
sql 
-- The part of the migration the ORM can't write (PostgreSQL)
ALTER TABLE tasks ALTER COLUMN position TYPE varchar(20) COLLATE "POSIX";
ALTER TABLE tasks ADD CONSTRAINT tasks_position UNIQUE (list_id, position) DEFERRABLE INITIALLY DEFERRED;

Rebalancing

When many moves land in the same gap, a move fails with a "position"LexicalError::Position error (see Maths). Space the positions again with rebalance and save the affected rows in one transaction. It is all or nothing: if the system has no room for every item it returns the error and changes nothing, so there is never a half-written order to save:

javascript 
const rebalanced = list.rebalance();
if (rebalanced.ok) {
  const [affected] = rebalanced.value;
  await db.transaction(async (tx) => {
    for (const item of affected) {
      await tx.query("UPDATE tasks SET position = $1 WHERE id = $2", [item.position.toString(), item.id]);
    }
  });
}
rust 
let mut tx = db.transaction()?;
for item in list.rebalance()? {
    tx.execute("UPDATE tasks SET position = $1 WHERE id = $2", (item.position().to_string(), item.id()))?;
}
tx.commit()?;

Restoring deleted items

With a soft delete (a deleted_at column) the item keeps its position, so restoring it puts it back exactly where it was, with a single write. If another item took the same position meanwhile, the unique constraint rejects the restore: load the rows together with the restored one using the untrusted optionset_untrusted (see below). The restored item gets a new position right after the other one, and it is the only row to save.

Concurrent users

Two users dropping two different items into the same gap at the same time can calculate the same position. The unique constraint makes the second write fail, so that client reloads the list and repeats the move with the new neighbors.

Without the constraint (or when merging old offline data), the duplicates reach the list. A normal set refuses them with a "not-ordered"NotOrdered error, and set(rows, { untrusted: true })set_untrusted(rows) repairs them: the first row keeps its position and the others get new positions right after it. Only the repaired rows are returned to be saved.

Positions coming from the browser are user input. Before storing one, rebuild it on the server with forge: a character that is not a digit of the system fails with an InvalidCharacterErrorPositionError::InvalidCharacter, and a position that is too long fails with an OverflowErrorPositionError::Overflow. Always use parameterized queries.

javascript 
const forged = system.forge(request.body.position);

}

Setup

If you came this far in the documentation, a big thank you for taking the time to read everything 🎉❗

Before choosing your own characters, keep in mind:

  • The digits are compared by their unicode value, so use characters from the Basic Multilingual Plane (up to U+FFFF). That way JavaScript, UTF-8 and UTF-16 compare them in the same order.
  • Avoid control characters (like the escape command \u001B). If you can, use the unicode PUA section.
  • Positions read from outside with forge are validated, any character that is not a digit of your system fails with an InvalidCharacterError (see Error Handling).

That validation is not a security measure, though. Staquia, or any library running in the frontend, cannot prevent someone from changing a string to a malicious command while it is sent to your server. Always check in your backend that a position uses only the expected characters before storing it, avoid attacks like SQL Injection with parameterized queries or a trusted ORM, or move your entire Staquia logic to the backend. Take the cybersecurity of your site seriously, bad security = money loss 💸!

Characters or bytes? A digit of the default system holds 10 bits but takes 2 bytes in UTF-8; an ASCII digit holds 6.5 bits in 1 byte. So the default system makes the shortest strings, and ascii or urlSafe the smallest indexes where the database or the protocol counts bytes.

The characters of urlSafe are the URL safe base64 ones, but sorted by their unicode value instead of the base64 order: positions are sort keys, not encoded data, so they keep the order a database compares them in. A range from first to last can't skip the unsafe characters between them, so these presets are sets of characters, and so can yours: Staquia.fromCharacters("0bcd…", ln, lz, fϰ)Staquia::from_characters(&"0bcd…", ln, lz, threshold) takes the zero followed by every digit, sorted by their code.

To choose your own values, pick a preset below and change it in the Setup App, or type your own characters. The formulas are explained in the Maths chapter.

Default: The shortest positions in characters, the best general choice for databases.

Note:  In Rust, ln + lz can be at most 32 (staquia::MAX_LENGTH), and Staquia::create returns a CreateError above it. A Rust Position keeps its digits in a fixed array of 32 instead of a heap allocated string: it is a small Copy value (88 bytes) that never allocates, which keeps creating and comparing positions cheap.

32 is more than real lists need:
  • The default system uses 20 (ln = 5, lz = 15), so it already has room to spare.
  • N never runs out in practice: with ln = 5 the default system stacks about 5.7 × 1014 items in each direction.
  • A longer Z only allows more moves into the same gap: 121 with the default 20, 242 with 32. Any limit is reached at some point, and then the list is rebalanced, which is a single transaction that keeps the order.
  • Every digit is stored in your database and its index: a digit takes up to 3 bytes in UTF-8 (2 with the default digits), so a position of 32 digits can take 96 bytes.
Only a very small base (a few digits) gains much from longer positions, and a bigger base is the better fix there. The sliders above go further because the JavaScript library has no fixed array.
Note:  Changing the configuration of a system that already has stored positions changes the meaning of their digits. To migrate them, read the rows sorted by their old position, clear their positions and load them into a list of the new system with the untrusted optionset_untrusted: every row gets a new position keeping the same order.
